Project introduction & technical design

Can software learn
what a person prefers?

This repository studies how a program can learn from someone's past choices, predict what they will prefer next, and adjust when those preferences change.

It contains a research plan, example data, and a small Python experiment. This document explains the problem, what the experiment does today, and how its files work together.

Start here / The research question

People's preferences depend on the situation.

Imagine an AI assistant helping someone write. The person repeatedly shortens its status updates but asks for more detail in explanations of research methods. Remembering “this person likes short answers” would miss half the pattern. A more useful understanding would be “short updates, detailed explanations.”

The long-term goal is an assistant that picks up these patterns without making the person repeat every instruction. It should also revise its understanding: a request for one unusually short explanation might be a temporary exception, while repeated requests could signal a lasting change.

This combines two research problems. Continual learning means improving as new experience arrives. Symbolic reasoning, in the intended future system, means working with explicit rules and exceptions that can be inspected and revised. The current code begins with a much simpler test of preference prediction.

What you can run today

A program reads a sequence of fictional choices between “concise” and “detailed.” Before revealing each choice, it asks three simple methods to predict it. It then reveals the answer, updates each method, and records the result.

A profile is the information a method currently remembers about one person. A context is the situation, such as a status update or a research explanation.

What this first test establishes

The experiment lets researchers compare ways of remembering preferences under controlled conditions. Because the people are simulated, their preferences and changes can be specified in advance.

The program does not read or generate actual writing, call a language model, or discover rules from conversation. Tests with real people are needed to learn whether these ideas improve AI assistance.

Predicting a choice comes first because it isolates the user model: does the program understand what this person would want? Producing an answer that satisfies that preference is a separate problem for a later experiment.

01 / How the program is organized

Input choices become predictions, updates, and a report.

Starting the program runs three Python modules, which are simply files containing related code. The entry module loads the choices. The experiment runner presents them in their original order and measures each prediction. The profile module supplies the three learning methods. Once the experiment finishes, the entry module writes the results to disk.

Every method receives the same choices, so comparisons use the same evidence. Each person has independent profiles, so one person's history cannot change another person's predictions.

03 / Following one choice through the program

The learner must guess before it sees the answer.

Suppose the next record says a person chose a detailed research explanation. The evaluator—the code that runs and scores the test—first tells the person's profile only that the context is “research.” The profile returns an estimated probability of choosing “detailed.” A value of 0.8 means an 80% estimate; 0.5 means neither choice is favored.

The evaluator compares that prediction with the actual choice, then gives the choice to the profile so it can learn. It saves a copy of the profile before and after the update. This order prevents the method from using the answer to predict itself.

{"user_id":"person-1", "context":"research", "choice":"detailed", "phase":"stable"}

user_id selects whose profile to use. context is the situation. choice is the answer revealed after prediction. Optional phase groups evaluation results and defaults to observed.

04 / The approaches being compared

Does remembering the situation improve the guess?

A baseline is a simple approach used as a point of comparison. This experiment includes one that never learns, one that remembers an overall preference, and one that also remembers preferences for particular situations. All three expose the same operations to the runner.

ModeWhat it remembersHow it guesses
uninformedNothing.Always assigns 50% to each choice.
flatHow often this person chose concise and detailed answers overall.Uses the overall balance to estimate the next choice.
conditionalThe overall counts, plus separate counts for each situation.Uses evidence from this situation, with the overall preference as a starting estimate.

A concrete example

A person often chooses concise status updates and detailed research explanations. A flat profile mixes those choices together. A conditional profile can keep the two patterns apart.

Both learning modes discount old evidence. On each update, relevant counts are multiplied by retention, then the new choice adds one. The default is 0.95.

A limitation worth studying

Context counts decay only when that context is observed; global counts change on every user observation. The conditional prior therefore also changes with evidence from other contexts.

This is recency weighting, not learned detection of an exception or lasting change. The model uses supplied context labels; it does not discover their meaning.

Exact probability calculation

Each pair stores concise count n and detailed count d. Flat probability is p = (d + 1) / (n + d + 2). Conditional probability is (d_context + 2 × p) / (n_context + d_context + 2). An unseen context therefore starts from the user's overall estimate. These are heuristic estimates for this changing-world experiment, not calibrated confidence guarantees.

05 / Running the experiment and interpreting results

Inspect both the score and the choices behind it.

Open a terminal in the repository's root directory. Python 3.11 or later is the only requirement. The first command below generates fictional choices, the second reads the small example file, and the third runs the automated checks. JSONL is a text format containing one JSON record per line.

Commands

python -m experiment --seed 7
python -m experiment --data data/examples.jsonl
python -m unittest discover -s tests -v

The default scenario contains 480 choices: four fictional people making 120 choices each. Situations alternate between research explanations and status updates. Each choice has a 10% chance of contradicting the simulated person's underlying preference. Research preferences briefly reverse, return, and later reverse permanently.

The seed fixes the random sequence, so repeating a command with the same code and settings reproduces the same choices and scores.

Accuracy measures how often the method favors the answer actually chosen; exact 50/50 guesses receive half credit. Brier score measures the error in its probability estimates, with lower scores being better. A confident wrong guess is penalized more than an uncertain one. Reports show both measures overall and during each phase of the scenario.

Files saved under reports/runs/

manifest.jsonExperiment settings, Python version, timestamp, and fingerprints of the input and source code. These help identify what produced a result.
predictions.jsonlThe detailed record: each choice, prediction, score, and profile before and after learning.
report.mdA readable comparison of the methods, with limits on interpretation.

The terminal prints the location of a fresh run-* directory. Earlier results are preserved. Generated results and the private-data directory are excluded from Git version control. The program currently holds the full input and prediction record in memory before saving.

Automated tests check that predictions cannot see the current answer, that users have separate profiles, that saved copies remain unchanged, that reporting labels do not affect learning, and that repeated seeds produce the same results. They also check rejection of malformed data. These checks establish that the experiment follows its rules; they do not establish usefulness for real people.

A good overall score can hide slow adjustment after preferences change, so the phase-by-phase results matter. This experiment reports one run at a time without statistical uncertainty estimates. Research conclusions would require repeated runs, comparisons across people and tasks, and validation with real users.

06 / From a controlled test to useful AI assistance

Future experiments address the parts this prototype leaves open.

The next step is to test predictions about actual artifacts, such as two alternative pieces of writing, using histories collected with participants' consent. A strong comparison would give a language model an automatically updated written profile or relevant past examples and ask whether a more structured representation improves its predictions.

Research stageWhat would be addedQuestion it answers
Real preference predictionActual choice pairs and language-model methods given equal access to past choices.Does individual history help predict preferences on unfamiliar tasks?
Revising beliefsExplicit preference rules, their supporting evidence, exceptions, and alternative explanations.Can the learner distinguish an unusual choice from a lasting change?
Asking useful questionsA limited number of clarification questions, compared with randomly selected questions.When does asking improve learning enough to justify interrupting the user?
Producing better workGenerated outputs rated without revealing which method produced them, plus measures of how much editing users need.Does understanding preferences lead to more useful assistance?
Carrying preferences across modelsCompare supplying a profile as instructions with training a small model-specific adapter, such as LoRA.Does training add value, and can the same preference evidence help a different model?

A LoRA adapter is a small set of learned changes attached to a compatible language model. It is one possible future way to apply a preference profile, not a component of the current program. The broader research goal is a reliable, revisable understanding of the user, regardless of how that understanding is applied.

06 / The new pluggable architecture

Change one part without rewriting the experiment.

The central Session in experiment/lab.py owns the episode state machine: start a task, expose public state, accept a question or complete artifact, run checks, collect user feedback, update memory, and finish. Everything around it is replaceable.

Plug-in pointBuilt-insExtension contract
RuntimeDemo, OpenRouter, command wrapperinvoke(Request) -> Response
Worker / userJSON LLM actorsWorker acts on public state; user reviews artifacts and answers questions.
Memory techniqueNo memory, profile, rules, skillscontext() and learn(evidence)
TaskEssay, webpage, generic filesPublic brief, safe files, objective check(), optional inspection.

JSON configuration connects components by name, or by a trusted module:Factory path. The worker never receives the private persona or independent assessment. MCP exposes the same session operations to an external harness, so API and harness studies can be compared under identical rules.
